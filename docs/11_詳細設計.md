# 詳細設計

## 1. 文書の目的

本書は、実装者が迷わず開発できるように、フロントエンド・バックエンド・データ設計・バリデーション・処理責務を整理する。

---

## 2. アーキテクチャ方針

### 想定方針
- フロントエンドとAPIを同一アプリケーション内で構成可能な設計
- UI表示、業務ロジック、データアクセスを分離する
- MVPではシンプルさを優先しつつ、責務の分離は保つ

### レイヤー案
1. Presentation
   - 画面
   - コンポーネント
   - フォーム
2. Application / Service
   - ダッシュボード集計
   - 月次収支集計
   - 要対応生成
3. Domain / Model
   - 物件
   - 部屋
   - 収入
   - 支出
   - 修繕
4. Infrastructure
   - DBアクセス
   - APIハンドラ

---

## 3. フロントエンド詳細設計方針

## 3.1 コンポーネント分類
- ページコンポーネント
- 一覧テーブルコンポーネント
- サマリーカードコンポーネント
- フォームコンポーネント
- 共通UI（ボタン、入力、モーダル、タグ）

## 3.2 状態管理方針
- 画面ローカル状態: フォーム入力、モーダル開閉
- サーバー状態: 物件一覧、詳細、集計データ、修繕履歴
- URLクエリ: 検索条件、対象月、絞り込み条件

## 3.3 バリデーション方針
- フロントで即時バリデーション
- APIでも同一ルールを再検証
- エラーは項目単位で表示

## 3.4 表示方針
- ダッシュボードはサマリーカード中心
- 一覧画面はPCで表形式を基本
- スマホではカードまたは横スクロールで対応

---

## 4. バックエンド詳細設計方針

## 4.1 サービス責務案

### PropertyService
- 物件一覧取得
- 物件登録
- 物件更新
- 物件詳細取得

### UnitService
- 部屋一覧取得
- 部屋登録
- 部屋更新
- 稼働状況集計

### FinanceService
- 収入登録
- 支出登録
- 月次収支集計
- 物件別収支集計

### RepairService
- 修繕履歴登録
- 修繕履歴一覧取得
- 未完了修繕抽出

### AttentionService
- 空室抽出
- 契約終了間近抽出
- 未完了修繕抽出
- 要対応一覧生成

### DashboardService
- KPI集計
- 注意対象物件抽出
- トップ画面向けデータ整形

---

## 4.2 API処理フロー例

### 物件登録API
1. リクエスト受信
2. 入力バリデーション
3. PropertyServiceへ委譲
4. 永続化
5. 201レスポンス返却

### 月次収支API
1. クエリパラメータ検証
2. FinanceServiceで収入・支出を集計
3. レスポンスDTOへ変換
4. 200レスポンス返却

### ダッシュボードAPI
1. 対象月検証
2. DashboardServiceがKPI集計
3. AttentionServiceの結果を取り込む
4. UI用レスポンス整形

---

## 5. データアクセス設計方針

- エンティティごとにデータアクセス責務を分ける
- 集計系は専用クエリまたはサービス側集約を利用する
- 一覧取得では絞り込み・並び替えを考慮する

### リポジトリ案
- PropertyRepository
- UnitRepository
- IncomeRepository
- ExpenseRepository
- RepairRepository
- LeaseContractRepository
- TaskRepository

---

## 6. 画面別の責務整理

| 画面 | 主責務 |
|---|---|
| ダッシュボード | KPI表示、注意対象への導線 |
| 物件一覧 | 比較しやすい一覧表示 |
| 物件詳細 | 1物件の横断把握 |
| 部屋一覧 | 稼働状況の確認 |
| 月次収支画面 | 月単位の収支把握 |
| 修繕履歴画面 | 履歴の蓄積と参照 |
| 要対応一覧 | 未処理事項の優先順位付け |

---

## 7. バリデーション定義（抜粋）

| 項目 | ルール |
|---|---|
| propertyName | 必須、100文字以内 |
| address | 必須、255文字以内 |
| purchasePrice | 0以上 |
| roomNumber | 必須、50文字以内 |
| floorArea | 0超 |
| rentAmount | 0以上 |
| amount | 1以上 |
| targetMonth | `YYYY-MM` 形式 |
| description | 必須 |

---

## 8. エラー表示方針

- 入力エラーは項目単位で表示
- 取得失敗時は再試行導線を出す
- データ0件はエラーではなく空状態として扱う
- サーバー障害時はユーザー向けに簡潔な説明を表示する

---

## 9. 将来拡張を考慮した設計ポイント

- 認証追加時にユーザーIDでデータ分離できるようにする
- マスタ追加に耐えられるカテゴリ設計にする
- CSVや外部連携を追加しやすいよう、集計ロジックをサービス層へ寄せる
- 利回りや分析ロジックは専用モジュール化できるようにする

---

## 10. フェーズ10時点の結論

詳細設計では、**一覧表示・集計・履歴管理・要対応抽出**を中心に責務を分離し、MVPの実装と将来拡張の両立を目指す。
