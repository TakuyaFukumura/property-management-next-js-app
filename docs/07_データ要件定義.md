# データ要件定義

## 1. 文書の目的

本書は、アプリで扱う主要データの種類、項目、関連、履歴管理の考え方を整理する。

---

## 2. データ設計の基本方針

- 物件を中心に、部屋、契約、収支、修繕、タスクを紐づける
- 集計しやすさと履歴参照性を重視する
- 初期は1人利用だが、将来の複数ユーザー化を妨げない
- 上書きよりも履歴保持を優先する領域を明確にする

---

## 3. 主要エンティティ一覧

| エンティティ | 説明 |
|---|---|
| User | 利用者情報 |
| Property | 物件情報 |
| Unit | 部屋情報 |
| Tenant | 入居者情報 |
| LeaseContract | 契約情報 |

## 6. 履歴管理方針

## 6.1 履歴を残す対象
- 契約
- 収入
- 支出
- 修繕履歴
- タスク更新履歴（必要に応じて）

## 6.2 上書き中心でもよい対象
- 物件基本情報
- 部屋基本情報

ただし、賃料変更など将来的に履歴保持が必要な項目は別テーブル化の余地を残す。

---

## 7. データ制約の考え方

- 金額項目は原則0以上
- 日付は妥当な形式で保持する
- 部屋番号は同一物件内で重複不可を検討する
- 必須項目未入力では保存不可
- ステータスは定義済みの値集合に限定する

---

## 8. 集計観点

### 8.1 月次収支集計
- 収入合計
- 支出合計
- 差額
- 物件別差額

### 8.2 稼働率・空室率集計
- 物件ごとの総部屋数
- 入居中部屋数
- 空室数

### 8.3 修繕分析
- 物件別修繕件数
- 月別修繕費
- 未完了修繕件数

## 10. フェーズ6時点の結論

データ設計は、**Propertyを中心とした一元管理モデル**を採用し、部屋・契約・収支・修繕・タスクを紐づけて保持する方針とする。
